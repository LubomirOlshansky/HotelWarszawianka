## Backlog
- fixed: the runtime city could freeze for good at the Palace. Since the Palace's Blender model became the default (#1100), a build of a sector that holds or reaches the Palace on the streamer's worker read the glb there (`load`, `Mesh.surface_get_arrays`), synchronous calls into the RenderingServer that wait for the main thread. When the main thread waited for that worker (a teleport, a tow, a respawn or a quit: sector_streamer.gd `_join_worker`), neither moved again. tajny-run stopped after 900 s at the race to Kemal's ("still waiting for the worker's build of s_-4_1"). Bisected on main's first-parent history with a probe that builds s_-4_1 on a thread: #1099 builds in 11.6 s, #1100 never ends. Now landmarks/centre.gd reads the glb's surfaces once on the main thread when the Landmarks are made (`warm_palace_glb`) and every build after reads that copy (`palace_glb_surfaces`); on a worker an unread glb gives the code model with a warning instead of a wait.
- added: `workerbuild` (check_worker_build.gd, CI group smoke): the Palace's sector builds on a second thread while the main thread only sleeps; it must end within 120 s. It fails on main before this change (stuck after 60 s) and passes after (19 s).
- found: the firstlife EXIT HANG (#1153) and the jump wait (#1160) are likely this same wait for a worker that waits for the main thread. Any other build code that calls `surface_get_arrays` or loads a file during a sector build can do the same (map_builder.gd `_mark_glow` does, on meshes it made itself).
